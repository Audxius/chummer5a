# Native interface direction

The user's priority is a coherent, uncluttered application alongside functional parity. New features must fit an existing workflow rather than add another permanent toolbar button.

- Keep the dark palette, with restrained accents for selection, primary actions, and status. Standard buttons use neutral borders; avoid decorative glow on routine interactions.
- Give each page a clear heading, a short description, search, and its main content. Keep page tools in a named menu when they are occasional actions.
- The user prefers the original inventory cards; keep those with the improved right-hand inspector. The selected item has a fixed header and Details, Manage, and Notes tabs; attachments show their parent breadcrumb. Combat/session controls stay in Details; editing, organization, and removal belong in Manage.
- Contact cards show a clean circular portrait, name, description and visual Connection/Loyalty ratings. Clicking the card opens a separate profile with the original large image, artwork inspection, full recorded details and editing. Do not restore the dropdown. Profiles display actual linked character attributes/skills and can open the whole linked sheet; do not fabricate NPC stats absent from the contact record. Use the original Pets & Cohorts category, with creation and character-file import. Keep enemy creation secondary; it is a legacy feature.
- Skills and Skill groups have separate first-class views. Show untrained/broken groups independently of the untrained-skill filter. Keep members, ratings and advancement together. Put occasional skill-creation actions and display options in menus, and preserve creation budgets.
- Info & Notes separates identity/appearance from full-area editors and named notebook pages stored inside the legacy Notes field.
- Keep all Edge actions in one special-attributes panel: advancement, available points, spend/regain/refresh, and permanent burn. Do not hide a single action behind a dropdown. Inventory shows equipped status on each item, without a separate equipped-loadout strip.
- Quality hover explanations include a short description, recorded modifiers and conditions, plus the source reference. Honor descriptions from custom data; identify missing prose rather than invent effects.
- Attributes and Overview use aligned, neutral panels with one clear presentation of each value. Attribute rows visibly include metatype bounds and augmented maximum; show current bounds too if they differ. Avoid redundant pips/bars and arbitrary left-aligned width caps. Ledger log and calendar bodies must fill the content area.
- Sorting and navigation hover must not change hit targets or layout. Keep decorative content out of hit testing; highlight selection and hover with clearly visible backgrounds and maintain readable muted text. Exercise repeated pointer moves at the center and edges and real clicks; do not rely on static screenshots for interaction reliability.
- Tooltips open near the hovered point, inside the window overlay, and must not intercept pointer input. Check positioning, stationary hover across rendered frames and pointer pass-through. Linux defaults to Avalonia's supported X11/XWayland backend; native Wayland is an explicit opt-in when XWayland is available. Headless interaction checks cannot establish compositor stability.
- Contact art shares illustration technique, not a repeated composition. Give each character their own pose, framing, expression, environment and palette. Preserve the user's stated joke: Slim Sulek is skinny, and Walter Black is Black.
- Keep creation tools together beside build validation and career conversion. Keep application settings and data tools together in the navigation rail. Actions must remain discoverable by ordinary clicks, rather than requiring right-click knowledge.
- Respect compact windows: scroll section navigation, wrap long details, and check the minimum supported window size. Inventory replaces category tabs with a selector at narrow widths. Do not truncate important specifications into tiny tiles.
- Exercise commands after reorganizing them. Render the changed screens and inspect them at full and compact sizes; a passing XAML build alone does not establish usable layout.

Further pages should adopt this hierarchy as their workflows are completed. The inventory redesign is an initial pass, not a declaration that the entire application has been reviewed.
